Why fine-grained authorization?

Most apps start with roles: admins can do everything, editors can edit, viewers can view. That breaks down as soon as the answer depends on which thing you are asking about: “can Anne edit this document?” depends on who owns it, which folder it sits in, which team shares that folder, and whether Anne is in that team.

Relationship-based access control (ReBAC) models permissions as a graph of relationships between users and objects — anne is a member of engineering, engineering can view product, product is the parent of roadmap — and answers “can X do Y on Z?” by finding a path through that graph. Roles still fit (a role is just a relation), but so do ownership, sharing, hierarchy and groups of groups.

The approach comes from Google’s Zanzibar paper (USENIX ATC 2019), which describes the system behind permissions in Drive, YouTube and other Google products.

What OpenFGA is

OpenFGA is an open-source, Zanzibar-inspired authorization engine. It was started at Auth0 / Okta and is a Cloud Native Computing Foundation incubating project. You run it as a service: your application writes relationships into it and asks it questions, instead of hard-coding permission logic.

  • Centralised — one place answers “who can do what” for every service.
  • Expressive — a small modeling language covers roles, ownership, sharing, hierarchies, groups and conditions.
  • Answerable both ways — not just “can she?”, but “what can she access?” and “who can access this?”.

This page is an independent explanation for learning. For the authoritative reference, see the official OpenFGA documentation.

Core concepts

Store

An isolated container holding one set of authorization models and relationship tuples — typically one per environment or tenant.

Authorization model

The schema: which types exist and how their relations are defined. Models are immutable; every write creates a new version with its own ID.

Type & object

A type is a kind of thing (doc, folder); an object is one instance, written type:id — doc:roadmap.

User (subject)

Who a tuple is about: an object like user:anne, everyone of a type user:*, or a userset like group:eng#member.

Relation

A named relationship a type defines — owner, parent, viewer — either assigned directly or computed from others.

Relationship tuple

One fact in the store: user · relation · object, e.g. user:anne owner doc:roadmap, optionally with a condition.

Userset

object#relation — “everyone who has relation on object”. Granting to group:eng#member grants to all members, present and future.

Check

The core question: is user related to object by relation? Answered by walking tuples according to the model.

Writing a model

Models are written in a small DSL. Each type lists its relations; each define says how that relation can be satisfied.

model
  schema 1.1

type user

type group
  relations
    define member: [user, group#member]   # people, or members of another group

type folder
  relations
    define owner: [user]
    define parent: [folder]
    define viewer: [user, user:*, group#member] or owner or viewer from parent

type doc
  relations
    define parent: [folder]
    define owner: [user]
    define editor: [user, group#member] or owner
    define viewer: [user, user:*, group#member] or editor or viewer from parent
    define blocked: [user]
    define can_comment: viewer but not blocked

The brackets list the type restrictions: which kinds of subject a tuple may assign directly. Everything after them describes how the relation is derived.

Conditions & context

Conditions attach a rule to a tuple, written in CEL and evaluated at check time with values from the tuple and the request:

type doc
  relations
    define viewer: [user with non_expired_grant]

condition non_expired_grant(current_time: timestamp, grant_time: timestamp, grant_duration: duration) {
  current_time < grant_time + grant_duration
}

Contextual tuples are tuples sent with a single request and never stored — useful for facts your app already knows at request time (the user’s current IP range, a session attribute, a group from a token).

How a check resolves

To answer “is user:bob a viewer of doc:roadmap?”, the resolver starts at the userset doc:roadmap#viewer and works down the definition until it reaches bob — or runs out of paths:

  1. viewer is a union, so try each branch. Direct tuples? Only user:dave. Editors? None that include bob. Then viewer from parent.
  2. Read doc:roadmap’s parent tuples: folder:product.
  3. Check viewer on folder:product: a tuple grants it to group:engineering#member.
  4. Is bob in that userset? user:bob member group:engineering — allowed.

Unions stop at the first branch that holds; intersections stop at the first that fails; exclusions check the base first, then make sure the subject is not in the excluded part.

Modeling tips

  • Start from the questions your app must ask (“can she comment?”), then define the relations that answer them.
  • Separate assignable from derived. Keep tuples on a few base relations (owner, member, parent) and compute the permissions (can_edit, can_view) from them.
  • Grant to usersets, not individuals — team#member keeps tuples few and changes cheap.
  • Use hierarchy (… from parent) instead of copying access down to every child.
  • Watch intersections and exclusions: they are powerful but make “why not?” harder; test them.
  • Test with assertions and write a new model version for every change — versions are immutable, so you can always compare.
